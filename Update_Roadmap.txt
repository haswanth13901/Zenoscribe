1. Frontend → React + Redux Toolkit (post-login pages)
Do this first, while the app is still small. Reason: subscriptions will need new UI (plan picker, billing page) — build that directly in React instead of writing more vanilla JS you'd just re-migrate later. Sequence: home.html (pilot, no realtime logic) → index.html/recorder → admin.html → translate.html last (WebSocket-driven, riskiest to port).

2. Postgres migration
Do this before going live, while there's little/no real user data to migrate. SQLite's single-file locking is fine for dev but not for a live multi-user deploy. db.py's raw SQL was written for exactly this swap.

3. Live deployment
Go live once the frontend is on React and the DB is production-grade — deploying on SQLite now just means re-migrating data under real traffic later.

4. Subscriptions (paid tiers/billing)
Last, since it's the highest-stakes item (money, compliance) and benefits most from a stable, deployed foundation with a React UI already in place to build the billing flow into.

Does this ordering match your thinking, or is there a reason you'd want e.g. Postgres or deployment earlier?
